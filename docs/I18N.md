# Localization

Glassmark shares one localization runtime between the desktop UI, extension popup, capture progress, picker and source-page capture controls.

## Files

- `app/i18n.js`: locale resolution, catalog fallback, interpolation, plural selection and marked DOM translation.
- `app/locales/en.js`, `zh-CN.js`, `ja.js`: complete message catalogs. Source messages are stable keys.
- `app/bootstrap.js`: loads the desktop language preference before importing the UI.
- `core/src/preferences.rs`: validates and persists `language` (`system`, `en`, `zh-CN`, `ja`).
- `scripts/build.mjs`: packages the shared runtime into extension bundles and supplies browser `_locales` metadata.

The desktop also publishes its resolved locale, so Follow system remains consistent even when the extension browser uses a different language. The extension reads the client's preference through capture options and remembers it for disconnected use. Capture scripts receive the locale explicitly; they do not read or write the source site's storage or change its document language.

## Adding UI text

Use `t(key, values)` for runtime text and explicit `data-i18n`, `data-i18n-title`, `data-i18n-aria-label`, `data-i18n-placeholder` or `data-i18n-alt` attributes for static app chrome. Never translate DOM subtrees containing archived content or user-defined labels.

Keep a complete sentence in one message. Put values into placeholders instead of joining translated fragments. HTML markup stays in the renderer, outside the catalogs. Values used in HTML must be escaped by the renderer; translations do not turn raw user content into trusted markup.

For count-dependent English text, use a catalog entry with `one`, `other` and `count` (the placeholder name). The runtime uses `Intl.PluralRules`; Chinese and Japanese can use invariant strings. Dates use the active locale through the shared `locale()` helper.

## Adding a language

1. Add a catalog with every source key and matching interpolation placeholders.
2. Register it in `app/i18n.js`, including locale resolution and date locale.
3. Add the language ID to preference validation and extension metadata in the build script.
4. Add UI and persistence coverage, then run `npm test` and the browser suite.

Unit tests check catalog parity, placeholder preservation, locale fallback, English plurals and known backend errors. Browser tests change languages through Settings, reload the app, verify the extension follows, and confirm user-authored names remain intact.
